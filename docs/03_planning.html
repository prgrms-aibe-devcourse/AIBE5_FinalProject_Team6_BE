Not Scope / KPI·SLO / Milestone

01 Not Scope
§3·02 기준으로, MVP에서 하지 않는 것과 외부로 위임하는 것을 분리해 둡니다. 범위를 줄인 이유는 “기능 나열”이 아니라 굿즈·드롭스·결제·커뮤니티에서 정합성·성능·운영 가능성을 수치로 증명하는 데 집중하기 위함입니다.
✕
자체 콘서트·팬미팅 좌석 예매(선점·좌석도·인앱 결제)
티켓 실물 좌석·PG 연동은 외부 플랫폼(인터파크 등) 책임. 공지·외부 링크 검증·노출만 제공.
✕
복수 PG · 인앱 티켓 결제
토스페이먼츠 단일. 멱등·웹훅·상태 복구에 리소스 집중.
✕
실시간 채팅
WebSocket 스케일·모더레이션 부담. 댓글·알림 중심.
✕
영상 업로드(자체 호스팅)
게시글은 이미지만. 라이브는 유튜브 등 임베드로 처리.
✕
추천 시스템 · Elasticsearch 전문 검색
ML·검색 인프라는 별도 도메인. MVP 조회는 캐시·인덱스·커서로 충분.
✕
Day-1 완전한 MSA
모듈러(멀티모듈) 모놀리스로 경계·의존성 증명 후, 필요 시 점진 분리.
✕
네이티브 모바일 앱
백엔드·API·관측·부하 검증이 목표. 클라이언트는 웹 FE 연동 수준.
✕
오프라인 재고 ERP 급 실시간 연동
명세상 Phase2·운영 복잡도 높음. MVP는 온라인 재고·품절·알림 중심.
  • 티켓은 팔지 않고 연결한다 — 정합성 범위를 명확히, 현실적인 타협.
  • 결제는 단일 PG로 깊게 — 멱등·웹훅·실패 복구에 집중.
  • 드롭스·재고·주문이 동시성 스토리의 중심축.
  • 문서·수치·장애 대응이 “기능 개수”보다 우선.


02 KPI / SLO — 목표 기준
부하 가정 (MVP 합의) 목표 비고
드롭스 오픈 순간 동시 ~1,000/~10,000 요청 급증 시나리오 (k6 스파이크) 대기열 + 오버셀 0 검증
상품·상점 Read ~300 RPS 구간에서 Read SLO 유지 목록·상세·캐시 히트 전제 명시
주문 생성 ~100 TPS 구간에서 Write P95 목표 합의치 조정 시 문서 버전 갱신
구분 SLO (목표 기준) 측정 방법
정합성 드롭스·상시 상품 오버셀·중복 주문 확정·중복 결제 0건 부하 후 DB·주문·결제 로그 교차 검증
결제 복구 결제 실패·웹훅 지연 시나리오에서 주문/재고 상태가 60초 내 일관 상태로 수렴 (팀 합의 기준: 자동 또는 수동 복구 절차 문서화) 웹훅 재전송·멱등키·수동 리컨실리에이션 로그
Write 성능 주문·결제·드롭스 쓰기 P95 < 300ms
 k6 + Grafana
Read 성능 피드·행사 등 Read P95 < 80~120ms, 상품 조회는 ~300 RPS 전제와 함께 기록
 k6 + Grafana
안정성 5xx < 0.1%, 타임아웃 임계 이하 로그 / APM
공정성·방어 Rate limit 위반 429 / 드롭스·오픈 구간 대기열·Depth 목표 차단 로그·큐 depth·대기 시간 분포
팀 규칙: 핵심 SLO 미달 시 기능 추가보다 원인·튜닝·계약 수정을 우선한다. “동작”이 아니라 측정·재현·개선 수치를 남긴다.
