01 왜 지금, 왜 이 문제인가

K-Pop 팬덤 시장은 이미 수조 원 규모로 성장했지만, 팬들이 실제로 사용하는 플랫폼 경험은 시장 규모를 전혀 따라가지 못하고 있습니다. 위버스·멜론티켓·네이버 쇼핑 등 기존 플랫폼들은 팬덤의 극단적인 트래픽 스파이크와 굿즈·결제 정합성이라는 특수성을 동시에 다루기 어렵습니다.

우리는 실제 팬 커뮤니티와 B2B 운영 사례를 분석하여, 기술적으로 해결 가능한 페인포인트와 그렇지 않은 것을 솔직하게 구분했습니다. 이 문서는 FANDROPS의 기능 범위가 어떤 현실 문제에서 출발했는지를 담습니다.

기존 플랫폼
위버스 · 멜론티켓 · 네이버 쇼핑 · 인터파크
대형 기획사 중심, 범용 이커머스 구조
우리가 보는 기회
소규모 운영 주체 + 오픈런 특화
기획사·1인 크리에이터·매니저 — 팬덤 특수성을 설계 1순위로 둔 플랫폼
02 발견한 페인포인트

각 항목에는 기술적으로 구현 범위에 포함되는지 여부를 함께 표시했습니다. 현실적 한계를 인정하는 것도 설계의 일부입니다.

💥
드롭 오픈 순간 서버 다운
위버스·멜론 등 기존 플랫폼은 굿즈·콘서트 오픈 순간 반복적으로 다운됩니다. 팬들은 새로고침을 반복하다 연결이 끊기고, 운영자는 기회를 날립니다. 평소의 100×–1,000×에 달하는 스파이크를 앞단에서 흡수하지 못하는 구조적 문제입니다.
구현 — Rate Limiting + Redis 대기열
🤖
매크로·비정상 트래픽 (굿즈·오픈 구간)
드롭스·상품 API에 비정상 호출이 몰리면 정상 팬이 불리해집니다. 완전 차단은 불가능하므로, Rate Limiting·대기열·429로 피해 최소화가 목표입니다.
콘서트·팬미팅은 외부 예매(F05)만.
구현 — Bucket4j · 대기열 depth 한계 — 100% 차단 불가
📦
드롭스·선착순 재고 오버셀
동시 요청 시 재고가 음수로 내려가거나, 품절인데 주문이 확정되는 사고가 납니다. MVP에서는 오버셀 0을 합격선으로 두고, 락·동시성 전략을 부하로 검증합니다.
구현 — 재고 동시성 · 부하 ~1k 동시
🔄
중복 결제 · 결제 실패 후 재고 미복구
결제 API 응답이 지연될 때 팬이 버튼을 여러 번 누르면 중복 결제가 발생합니다. 또한 결제 실패 후 선점된 재고가 복구되지 않아 품절로 표시되는 현상이 반복됩니다. 멱등 키로 중복 결제를 막고, Saga 보상 트랜잭션으로 실패 시 재고를 자동 복구합니다.
구현 — Saga · Outbox
🔔
품절 상품 재입고 알림 미작동
품절 후 재입고돼도 팬이 모르면 다시 놓칩니다. 재입고 관심 등록 → 도메인 이벤트 발행 → 알림 전송 파이프라인으로 해결합니다.
구현 — 발행/전송 분리
🏪
오프라인·ERP급 재고와 온라인 실시간 불일치
현장 판매·ERP와 온라인 재고를 실시간 단일화하는 요구는 현실적으로 무겁습니다. MVP는 온라인 재고·품절·재입고 알림에 집중하고, 오프라인 ERP 연동은 하지 않습니다.
Not Scope — 03
🏆
팬 충성도·출석 점수 기반 드롭 우선권
리서치에서 “구매·출석 이력으로 선착순 우선권” 아이디어가 나왔으나, 확정 MVP 명세에는 팬 등급·포인트·드롭 우선 접근권이 없습니다. 대신 대기열·공정한 레이트리밋으로 오픈 구간을 다룹니다.
Not Scope — 팬 등급·우선권 시스템
📅
아티스트 스케줄을 한눈에 볼 수 없음
팬들은 트위터·공식 홈페이지·위버스를 번갈아 보며 일정을 직접 취합해야 합니다. 아티스트 단위 캘린더로 드롭·팬미팅·라이브 일정을 통합 제공하고, 라이브 시작 시 푸시 알림을 발송합니다.
구현 — 일정·미디어
✨
팬덤 서비스의 체류 구조 — 아티스트가 메인 콘텐츠
일반 이커머스와 달리 팬덤 플랫폼의 중심은 아티스트(그룹·멤버)입니다. 팬은 특정 아티스트를 팔로우한 뒤 그 아티스트 공간(피드·굿즈투표·일정·드롭스) 안에서 오래 머무르는 것이 자연스러운 사용 패턴입니다. 메인 화면의 범용 참여형 이벤트보다, 아티스트 단위 커뮤니티·커머스가 체류와 재방문을 만든다는 전제로 MVP를 설계합니다.
MVP — F03-01 아티스트 홈 · F03-08 굿즈투표
💬
댓글 도배·커뮤니티 품질
댓글·하트에서 스팸·도배가 발생할 수 있습니다. MVP는 기본 정책·레이트·도배 방어 수준으로 다루고, 아티스트가 직접 운영하는 금칙어 사전·신고 누적 영구 차단 같은 무거운 모더레이션 제품은 범위에서 뺍니다.
구현 — 댓글·정책·도배 Not Scope — 아티스트별 금칙어·신고 제재 시스템
✈️
해외 배송 현황을 실시간으로 확인할 수 없음
글로벌 팬들이 국제 배송 상태를 플랫폼 내에서 실시간으로 확인하고 싶어 합니다. 외부 배송 API 연동으로 타임라인 형태의 배송 추적을 제공하자는 아이디어가 있습니다. 단, 국제 배송 API는 캐리어마다 규격이 다르고 안정성이 낮아 현실적으로 구현이 매우 어렵습니다. MVP 범위에서 제외하고, 국내 배송 기본 상태 조회에 집중합니다.
MVP 제외 — 구현 복잡도 과다 국내 배송 기본 조회만 포함
03 기술적 한계 — 솔직한 정리

좋은 설계는 할 수 있는 것만큼, 할 수 없는 것을 명확히 아는 것에서 나옵니다.

  • 티켓은 팔지 않고 연결한다. 행사 안내 + 외부 링크 검증·노출만.
  • 매크로 완전 차단은 불가능하다. 충분히 정교한 봇은 사람과 구분이 어렵다. Rate Limiting·본인인증·팬 등급 우선권으로 봇의 수익성을 낮추는 것이 현실적인 목표다.
  • 오프라인 ERP급 재고 연동은 MVP 제외. 온라인 재고·오버셀 0·재입고 알림에 집중.
  • 팬 등급·출석 포인트 우선권은 복잡도가 높아질 우려가 있다. 리서치 아이디어로 남긴다.
  • 해외 배송 실시간 타임라인은 MVP에서 제외한다. 국제 물류 API는 캐리어별 규격 통일이 안 되어 있고 신뢰도가 낮다. 이 문제에 리소스를 쓰는 것보다 정합성·동시성 핵심 과제에 집중하는 것이 포트폴리오 가치가 높다.
04 페인포인트 → MVP 기능 도출

위 페인포인트를 해결하기 위해 도출된 핵심 기능 요구사항입니다. SSOT: §1 · 04 IA · 03 기획.

페인포인트 → 기능 매핑
인프라
서버 다운 → Redis 대기열 (Sorted Set) + Rate Limiting (Bucket4j)으로 트래픽 흡수. 대기 순번 SSE 실시간 안내.
재고
재입고 알림 미작동 → 재입고 구독 + Kafka 이벤트 발행. ERP Not Scope.
결제
중복 결제·재고 미복구 → 멱등 키 + Saga 보상 트랜잭션 + Outbox 패턴. 실패 60초 내 자동 복구.
캘린더
스케줄 파편화 → 아티스트 단위 통합 캘린더. 드롭·팬미팅·라이브 일정 통합 표시. 라이브 시작 알림 발송.
알림
재입고·결제완료·라이브·커뮤니티 → 발행(도메인 오너) / 전송(표지민) 표로 고정. Kafka 필수 아님.
